# FlashTrie Examples

Runnable examples that reproduce the latency measurements reported in the
FlashTrie paper: constrained beam search over a GPU-resident succinct trie.

Everything here talks to the compiled `flashtrie` extension through one small
wrapper, [`flashtrie_bench.py`](flashtrie_bench.py), which uses only the API
the C++/CUDA sources in this repository actually export.

| File | Purpose |
| --- | --- |
| [`flashtrie_bench.py`](flashtrie_bench.py) | Shared wrapper: extension loading, TSV parsing, batching, the searcher, latency statistics |
| [`make_example_data.py`](make_example_data.py) | Builds a synthetic trie and proposal files so the examples run with no proprietary data |
| [`run_trie_search.py`](run_trie_search.py) | Single-configuration benchmark |
| [`run_trie_search_BWsweep.py`](run_trie_search_BWsweep.py) | Beam-width sweep |
| [`run_trie_search_BSsweep.py`](run_trie_search_BSsweep.py) | Batch-size sweep |

## Quick start

Build the extension first (see the [top-level README](../README.md)), then:

```bash
cd examples

# 1. Generate a synthetic constraint library and proposal grids.
python make_example_data.py --per-topk-files 100,600,1000

# 2. Benchmark one configuration.
python run_trie_search.py \
    --trie-path data/trie.bin \
    --data-path data/topk/output_topk100.tsv \
    --beam-size 100 --topk-tokens 100 \
    --latency-out out/latency.tsv

# 3. Sweep beam width.
python run_trie_search_BWsweep.py \
    --trie-path data/trie.bin \
    --data-path 'data/topk/output_topk*.tsv' \
    --file-values 100 600 1000 --onemap \
    --output-dir out/bw
```

The scripts locate the extension automatically in `../build/tools`. Override
with `FLASHTRIE_BUILD_DIR` if you built somewhere else.

## Measurement setup

Latency at this scale is sensitive to NUMA placement and to the scheduler
migrating the host thread across cores. Pin the process to a single NUMA node
for stable numbers, as we did for every measurement in the paper:

```bash
numactl --cpunodebind=0 --membind=0 taskset -c 0-7 \
    python run_trie_search.py --trie-path ... --data-path ...
```

The same prefix applies to the sweep drivers, which pass their environment
down to each child run.

Two further notes:

- **Run on an idle GPU.** A competing process on the same device inflates
  measured latency by more than an order of magnitude.
- **Absolute numbers depend on the constraint library.** The synthetic data
  generated by `make_example_data.py` is much smaller than the 762M-key
  library used in the paper, so treat it as a correctness and scaling demo,
  not a reproduction of the reported milliseconds.

## Input format

Both real and synthetic runs consume the same tab-separated layout: one query
per line, with a JSON object holding the per-step top-K proposals.

| Field | Meaning |
| --- | --- |
| `topk_id` | `[max_seq_length][K]` token ids proposed at each decoding step |
| `topk_logp` | `[max_seq_length][K]` matching log-probabilities |
| `lcid` | Optional. A token id to force as the first step |

`topk_id` rows are stored sorted by token id, which is what the kernel's
binary child search requires.

## `run_trie_search.py`

Benchmarks a single configuration. It runs `--num-runs` passes over the data,
discards the first as warm-up, and reports the mean and percentiles across the
remaining passes.

```bash
python run_trie_search.py \
    --trie-path data/trie.bin \
    --data-path data/topk/output_topk1000.tsv \
    --beam-size 1000 --topk-tokens 1000 \
    --batch-size 1 \
    --latency-out out/latency_bw1000.tsv \
    --output-path out/results_bw1000.tsv
```

### Search options

| Flag | Default | Meaning |
| --- | --- | --- |
| `--beam-size` | `100` | Beam width `B`; hypotheses kept per step |
| `--topk-tokens` | `8` | Proposals `K` considered per hypothesis per step |
| `--superset-topk` | off | Input file holds more than `K` proposals per step; select the `K` highest-probability ones and re-sort by token id |
| `--token-logp-threshold` | `-10.0` | Prune a candidate token below this log-probability |
| `--sent-logp-threshold` | `-40.0` | Prune a hypothesis below this cumulative log-probability |
| `--length-norm` | `5.0` | Length-normalisation exponent applied when ranking |
| `--early-exit` | off | Stop a beam once every hypothesis has terminated |
| `--trie-start-token` | none | Force a first-step token. Omit it to search from the trie root, which is what the paper's runs do. Pass an integer to force that id, or `lcid` to read it from each record |
| `--max-seq-length` | `64` | Maximum decoding steps |

`--trie-start-token` is worth calling out: forcing a prefix restricts the
search to one subtree, and if the trie has no matching child the run returns
no results at all. Leave it unset unless your data really is organised that
way.

### Execution options

| Flag | Default | Meaning |
| --- | --- | --- |
| `--batch-size` | `1` | Requests per kernel launch |
| `--cpu` | off | Run the CPU reference path instead of the GPU kernel |
| `--num-runs` | `11` | Passes over the data; the first is warm-up |
| `--max-queries` | all | Truncate the input, useful for smoke tests |
| `--logging-steps` | `1000` | Progress-print interval |
| `--phase-out` | none | Write the per-phase GPU breakdown (needs `-DTBS_PROFILE`) |

### Checking constraint equivalence

The CPU and GPU paths implement the same search and return the same candidate
set. GPU execution changes the cost of constrained beam search, not its
semantics:

```bash
python run_trie_search.py ... --max-queries 20 --output-path out/gpu.tsv
python run_trie_search.py ... --max-queries 20 --output-path out/cpu.tsv --cpu

python - <<'EOF'
def load(path):
    rows = {}
    for line in open(path):
        f = line.rstrip("\n").split("\t")
        if len(f) >= 3:
            rows[f[0]] = set(s.strip() for s in f[2].split("|"))
    return rows

gpu, cpu = load("out/gpu.tsv"), load("out/cpu.tsv")
differing = [q for q in gpu if gpu[q] != cpu[q]]
print(f"{len(gpu)} queries, {len(differing)} with differing result sets")
EOF
```

Compare sets rather than running `diff`. The two paths break ties between
equal-scoring candidates in different orders, so their line ordering can
differ even though the retrieved sets match. Exact score ties are rare in real
proposal distributions but common in synthetic data.

The CPU path is dramatically slower, so pair it with `--max-queries`.

### Latency output

`--latency-out` writes a two-line TSV with these columns:

```
beam  topk  batch_size  batches_per_run  num_measured_runs
mean_ms  std_ms  p50_ms  std_p50_ms  p90_ms  std_p90_ms
p95_ms  std_p95_ms  p99_ms  std_p99_ms  mean_qps  std_qps
```

Each percentile is computed within a pass; the reported standard deviation is
across passes.

## `run_trie_search_BWsweep.py`

Sweeps beam width and collects every run into one `latency_summary.tsv`.

The paper's sweep uses one input file per beam width, where the filename's `K`
is used as both the beam width and the top-K. Pass the file set as a template
containing a single `*`, with `--file-values` supplying the substitutions, and
add `--onemap` to pair each file with its own configuration:

```bash
python run_trie_search_BWsweep.py \
    --trie-path data/trie.bin \
    --data-path 'data/topk/output_topk*.tsv' \
    --file-values 100 200 400 600 800 1000 \
    --onemap \
    --batch-size 1 \
    --output-dir out/bw
```

Quote the template so the shell does not expand the `*` itself. Without
`--onemap` the driver takes the cartesian product of inputs and configurations
instead.

Alternatively, drive several configurations from a single wide input file with
`--beam-topk` and `--superset-topk`:

```bash
python run_trie_search_BWsweep.py \
    --trie-path data/trie.bin \
    --data-path data/topk.tsv \
    --beam-topk 100:8 600:8 1000:8 \
    --superset-topk \
    --output-dir out/bw
```

Add `--skip-existing` to resume an interrupted sweep, and `--cpu`,
`--early-exit`, `--max-queries` or `--phase-timing` to forward those options to
every child run.

## `run_trie_search_BSsweep.py`

Sweeps batch size for each beam configuration, measuring how throughput scales
as requests share a kernel launch.

*Directory mode* mirrors the beam-width sweep's `--onemap` convention: point it
at a directory of `output_topk{K}.tsv` files and each `K` becomes both the beam
width and the top-K.

```bash
python run_trie_search_BSsweep.py \
    --trie-path data/trie.bin \
    --data-path data/topk \
    --topk-values 100,600,1000 \
    --batch-sizes 1,2,4,8,16,32 \
    --output-dir out/bs
```

*Single-file mode* takes explicit `beam:topk` pairs from one wide file:

```bash
python run_trie_search_BSsweep.py \
    --trie-path data/trie.bin \
    --data-path data/topk.tsv \
    --bw-topk-pairs 100:8,600:8,1000:8 \
    --batch-sizes 1,4,16 \
    --superset-topk \
    --output-dir out/bs
```

## `make_example_data.py`

Generates a synthetic constraint library and matching proposal grids, so the
examples are runnable without the proprietary keyword data used in the paper.

```bash
python make_example_data.py \
    --num-keys 1000000 \
    --vocab-size 262144 \
    --per-topk-files 100,600,1000 \
    --num-queries 2000
```

| Flag | Default | Meaning |
| --- | --- | --- |
| `--out-dir` | `data` | Where to write `trie.bin` and the proposal files |
| `--num-keys` | `1000000` | Keys in the synthetic constraint library |
| `--key-length` | `8` | Maximum tokens per key |
| `--length-weights` | `2,10,45,25,10,5,2,1` | Relative frequency of key lengths 1, 2, 3, … The default approximates a real tokenized keyword library, where most keys are 2–4 tokens |
| `--vocab-size` | `262144` | Synthetic token vocabulary size |
| `--num-queries` | `2000` | Queries per proposal file |
| `--topk` | `100` | Proposals per step, single-file mode |
| `--per-topk-files` | none | Comma-separated `K` values; writes `topk/output_topk{K}.tsv` for each, the layout the sweeps consume |
| `--seeds-per-query` | `128` | Valid keys seeded into each query's proposal grid |
| `--write-keys` | off | Also write the plain-text key list, which `marisa-build` can consume directly |

`--seeds-per-query` controls how much of each proposal grid lies on a real
trie path. Set it too low and the search legitimately returns nothing, because
no combination of proposed tokens spells a key in the library.
